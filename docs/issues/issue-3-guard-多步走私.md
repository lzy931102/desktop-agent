# Issue #3：guard 多步走私——逐调用风险评估的固有边界

- 状态：**待评估，非本期范围**（2026-09-26 记录，架构级改动，不塞进 guard 加固）
- 发现：第三期 format 误伤修复评估期间
- 关联：issue #2（guard 匹配逻辑加固，已完成三期）；类别 6 裸词判定表中
  "format 不拦裸词"的残余风险即来源于此

## 一、问题

guard.evaluate 按**单次工具调用**做风险评估。危险命令可以被拆成多次
无害调用完成，单次看每次都不命中：

```
type_text {"text": "format"}     → none（裸词不拦，见 issue #2 类别 6 判定表）
type_text {"text": " c:"}        → none（无命令词）
press_key {"key": "enter"}       → none
```

三次调用在 cmd 里串联执行，效果等价于 `format c:`，但每一步的单次
评估都合法。同理可拆 `del` / 旗标 / 目标 / 回车，或用剪贴板 +
press_key 组合拼装任意命令。

## 二、为什么单次评估挡不住

1. **单次调用本身确实无害**：`type_text "format"` 只是往剪贴板/输入框
   敲了 6 个字符。危险在"多次调用的组合效果"，而组合效果只有跨调用
   才可见。
2. **单次评估无状态**：evaluate(tool, args) 是纯函数，不记得上一次
   敲了什么。任何"最近 N 次输入拼起来像命令"的判断都需要会话级状态。
3. **误伤不可接受**：把单次文本匹配放宽（如拦裸词 format）会误伤
   "date format: YYYY-MM-DD" 这类高频正常文本（第一期已实证此误伤，
   第三期已修复为盘符形态校验）。逐调用框架内没有既不漏又不误伤的解。

## 三、解法方向（会话级状态，均属架构级改动）

| 方向 | 思路 | 代价/风险 |
|---|---|---|
| A. 会话输入滚动窗口 | agent_loop 维护本次任务内 type_text/clipboard 内容的滑动摘要，evaluate 增加可选的 context 参数，命中"命令词碎片拼接"时升级为 high 送确认 | 需改 evaluate 签名与全部调用方；窗口多大算"拼接"需调参，存在新误伤面 |
| B. 危险词计数器 | 同一会话内出现命令词（format/del/rd…）即计数，达到阈值（如出现命令词后又出现盘符/回车）送确认 | 状态逻辑简单，但阈值与组合规则是一套新策略面，需要独立拍板与测试 |
| C. 高危终端场景整体升级 | 检测到 cmd/PowerShell 前台时，所有 type_text 一律走 medium/high 确认 | 实现最简单，但终端内合法操作（dir、cd）全部被搅扰，可用性损失大 |

三个方向共同前提：**审批流（approval）已现成**，缺的只是"跨调用聚合
信号"的产生位置。个人倾向 B（信号面最小、可控可测），但属架构决策，
需独立评估后再立项。

## 四、影响面

- 核心改动点：agent_loop（会话状态维护）+ core/guard（evaluate 签名
  或新增 context 通道）+ 全部调用方与测试基建（当前测试假定 evaluate
  无状态）。
- 不影响：medium 分级、审批桥、审计链（均已就位，聚合信号只是多一种
  触发 high 的来源）。
- 现实风险评估：本产品为本地单用户 Agent，威胁模型是"防被诱导执行"
  而非"防本机用户对抗"；多步走私需要 LLM 连续多步被精确诱导，实际
  触发概率低——这也是它排期靠后的原因。

## 五、决议

- 本期（guard 加固三期收尾）**不实现**，仅立此存照。
- 待办：与 B 方向相关的阈值/组合规则设计需单独拍板后再开工。
