## 2. P0（会实际造成损害，建议优先处理）

### P0-1　`.gitignore` 把 `__init__.py` 吃掉了 —— 提交即缺文件

**证据**（三条独立命令，全部实测）：

```bash
$ git check-ignore -v plugin_system/__init__.py
.gitignore:26:_*.py	plugin_system/__init__.py      # ← 命中

$ git add --dry-run plugin_system/
add 'plugin_system/contract.py'
add 'plugin_system/manager.py'
add 'plugin_system/sample.py'                          # ← 没有 __init__.py

$ git ls-files | grep __init__
（空）                                                  # ← 仓库里一个 __init__.py 都没有
```

`.gitignore` 第 26 行的 `_*.py`（本意是忽略临时脚本）用 `*` 匹配了 `_init`，
把**所有 `__init__.py` 都排除在外**。

**为什么以前没炸**：`core/__init__.py` 的正文只是模块清单注释，丢了也不影响——
Python 3.3+ 的命名空间包机制会让 `from core.paths import data_dir` 照常工作。
所以这个规则从 `core/` 时代就带着这个缺陷，一直侥幸无害。

**为什么现在会炸**：`plugin_system/__init__.py` 是**有实际导出逻辑的**：

```python
from .contract import PluginContractError, PluginInfo, PluginTool
from .manager import PluginManager      # ← 公开入口
```

它一旦不入库，`from plugin_system import PluginManager` 在干净环境里**必然 ImportError**。
而这条 import 正好出现在：
- `test_plugin_system.py:13`、`test_plugin_boundary.py:25`（两个新测试同时红）
- 未来 gui.py / agent_loop.py 的接入代码

**风险特征**：本地全绿（文件在本地存在）、远端必红，只有 clone 或他人复现时才暴露；
且 `.gitignore` 那行看起来完全无害。属于最容易漏过自查的一类。

**修法**（改前请先 `git status` 确认范围）：

```bash
# 1) .gitignore 在 `_*.py` 之后补一行否定规则（顺序不能反）
!**/__init__.py

# 2) 验证规则已生效（应无输出）
git check-ignore -v plugin_system/__init__.py core/__init__.py

# 3) 补回两个包的入口文件
git add plugin_system/__init__.py core/__init__.py

# 4) 确认提交清单完整（应能看到 4 个 plugin_system 文件）
git add --dry-run plugin_system/
```

**建议加一条守护**：提交后按工作准则第七节做 `git show --stat` 核对，专门看"新增包的
`__init__.py` 是否在列表里"。这类问题靠跑测试发现不了（本地文件总是存在）。

### P0-2　插件模块有 1 条测试从未通过，且当前处于未提交状态

**证据**（实测输出）：

```
test_plugin_system.py:285: AssertionError
assert ['插件甲', '插件甲'] == ['插件甲', '测试插件', '测试插件']
1 failed, 21 passed
```

**根因是两层叠加**：

1. `test_output_order_stable_by_stem` 里三个插件文件都用同一份 `GOOD_PLUGIN`，
   只替换了 `NAME`，工具名全是 `test_tool_a` / `test_tool_b`
   → 跨插件工具撞名，**只有 `aaa` 加载成功**（`bbb`/`ccc` 被正确拒绝）。
   `enabled_tools()` 因此只有 2 个工具，且都属"插件甲"。
2. 断言的期望值本身也写错了：`["插件甲", "测试插件", "测试插件"]` 既数量不对、
   名字也不对（第三个本该是"插件乙"）。

**附带收获**：这条失败**恰好证明撞名防线在工作**（`bbb`/`ccc` 被拒且错误信息可读）。
建议拆成两条测试：一条用三个互不撞名的插件验证排序，一条专门验证跨插件撞名拒绝。

**修法**：

```python
write_plugin(tmp_path, "bbb", GOOD_PLUGIN.replace("test_tool_a", "t_bbb_a")
                                        .replace("test_tool_b", "t_bbb_b"))
# aaa → 插件甲 / ccc → 插件乙，工具名同样各自不同
assert [t.plugin_name for t in m.enabled_tools()] == \
    ["插件甲", "测试插件", "插件乙"]
```

**流程问题（比代码问题更值得注意）**：这说明新模块**没跑完全部测试就留在了工作区**，
且已存在 1 小时以上未提交。对照工作准则：
- 五.3「对照组不能丢：新增测试后，原有全部用例必须仍 PASS」—— 现在是 1 failed
- 十三红线「声称'已修复'但无复测结果」
- 七.1「完成一个可交付单元就提交，不攒大提交」—— 当前 `plugin_system/` + 2 个测试 +
  `core/settings.py` + `core/paths.py` + 2 份 docs + release notes 全部挂在工作区

### P0-3　方案 §5 的接入示例与实现契约不符，照抄必错

`plugin_system` 的实现返回 **`PluginTool` 数据类**（`contract.py:50-67`），
而方案 §4 写的是 `enabled_tools() -> list[dict]`，§5 的示例代码全部用**字典下标**：

```python
self._plugin_tools = plugins.enabled_tools() if plugins else []
plugin_tool = next((t for t in self._plugin_tools if t["name"] == name), None)   # ← TypeError
... "name": t["name"], "description": t["description"], "parameters": t["parameters"]
```

`PluginTool` 是 dataclass，`t["name"]` 必然 `TypeError`。正确写法是属性访问：

```python
tool = next((t for t in self._plugin_tools if t.name == name), None)
schema = t.schema()          # 已内置 OpenAI function 格式转换
t.run / t.prompt_hint / t.default_risk / t.plugin_name
```

**同一处还有两个隐藏问题**：

1. §5 的插件分支 `return str(plugin_tool["run"](args))` **没有 try/except**，
   而 §8.6 明确写"插件 run() 抛异常时在 `_execute_tool` 捕获"——**文档自相矛盾**。
   照抄的结果：插件抛异常会冒到 `run()` 顶层（`agent_loop.py:896-901`），
   **整个任务失败**，而不是"插件级错误隔离"。这与方案 §8"坏插件不拖垮主程序"的承诺不符
   （加载期隔离了，运行期没有）。
2. 插件分支绕过了 `run_with_retry` 和 `_verify_action`（内置工具的待遇），
   等于"插件工具永不重试、永不校验"。目前 `guard.is_retryable(未知工具)` 返回 `False`
   → 天然不重试，**这个默认值是安全的**，但方案没写明，容易被后续改动破坏。

### P0-4　插件的风险兜底会污染界面语义与审计

契约 `DEFAULT_RISK = "medium"`（`contract.py:29`）本身是对的（fail-closed）。
但 `agent_loop.py:989-994` 对 medium 的处理是：

```python
if self.auditor:
    self.auditor.emit("medium_risk", tool=name, reason=reason)
self._log(f"[敏感操作] {name}：{reason}（已放行并记入审计）")
```

**后果**：插件作者忘写 `default_risk` 时（默认 medium），用户每调用一次插件，
界面上就多一行"[敏感操作] query_weather：…（已放行并记入审计）"。
用户装的只是一个"查天气"插件，却被告知"敏感操作" → 既误导又刷屏，
违反工作准则四.6「克制，不打扰」。

**修法（二选一，建议 A）**：
- **A**：插件工具的兜底 medium 只写审计，不显示"[敏感操作]"界面行——即在 risk 元组里
  带上来源标记（如 `("medium", reason, "plugin")`），界面层只对内置工具的 medium 显示提示。
- **B**：兜底等级与界面提示解耦，插件默认 medium 仅用于"是否走审批"的判断。
