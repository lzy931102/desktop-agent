## T6（P0）open_app 支持浏览器 + 确定性错误不重试

- **证据（audit-20260930.jsonl 实录）**：
  - 21:41:09 `open_app("edge")` → retry×3 → 错误"仅支持直接打开: 记事本/计算器/…"；
  - 21:45:27、21:49:41、21:52:44 三次 `open_app("chrome")` 同样 retry×3。
  - 12 次 retry 全部是**确定性拒绝**的重放，每次白等 1+2+4=7 秒、多占 3 条审计、3 个轮次预算。
- **根因**：
  - `_open_app` 的 `app_map`（`agent_loop.py:757-764`）无任何浏览器条目；桌面任务最高频的场景（"打开浏览器访问 xx"）只能靠 win 菜单敲字绕行，单是开浏览器就烧掉 4–5 轮。
  - `run_with_retry`（`core/retry.py`）只看返回文本含"错误"就重试，不区分**瞬时失败**（窗口未出现）与**确定性拒绝**（白名单未命中、参数校验失败）——后者重试注定失败。
- **修改方案**：
  1. **加浏览器入口**，二选一（推荐 B）：
     - A. `app_map` 增加浏览器条目（exe 路径硬编码常量 + 启动前 `Path.exists()` 探测，路径探测不到给出明确错误）；
     - B. 新增 `open_url(url)` 工具：仅接受 http/https，复用 `core.settings.validate_public_https` 校验，`os.startfile(url)` 交给系统默认浏览器——不碰 exe 路径，注入面最小，且"开浏览器访问 xx"一步到位。
  2. **重试策略区分确定性失败**：给工具失败的返回加"不可重试"标记（如返回前缀约定 `错误: 不支持…`/`错误: 仅支持…`，或工具侧返回结构化结果），`run_with_retry` 对确定性拒绝立即返回不重试；同步更新 `SYSTEM_PROMPT`（`agent_loop.py:873/884`）里的工具说明。
- **验收标准**：
  - 实测任务"开 Chrome 访问百度搜索今天天气"能在 ≤10 轮内完成（对照当晚 `7ade93a6` 失败案）；
  - `open_app("chrome")`（或 `open_url`）不再出现 retry 审计记录；
  - 新增单测：白名单外应用首次即返回、`run_with_retry` 对确定性拒绝 attempts==1。
- **预估工时**：1–2h　**依赖**：无
- **实施记录（2026-10-01，已完成，采用方案 B）**：
  - 新增 `open_url(url)` 工具（`agent_loop._open_url`）：`core.settings.validate_public_url`
    （由 `validate_public_https` 泛化，允许 http/https，同样拒绝 localhost/内网/
    保留地址——含域名解析到内网的绕过）；guard 定级 medium（出网动作，与发飞书同级）；
    不入 RETRYABLE_TOOLS（校验/startfile 失败均为确定性）；SYSTEM_PROMPT 与
    TOOLS_SCHEMA 已同步；`plugin_system.contract.RESERVED_TOOL_NAMES` 已补 `open_url`
    （边界测试如约变红后同步）。
  - `core/retry.py` 新增 `is_permanent_failure`：`NON_RETRYABLE_MARKERS` 命中即停。
    标记两轮扩充：首发"仅支持/不支持/无法识别/请先填写"；重放实测后补 UIA 系列
    "找不到窗口/找不到标题包含/找不到名为/没有可见窗口/没有任何可枚举"
    （`list_ui_elements("旧窗口名")` 页面跳转后 4 次 UIA 超时烧 8 分钟的实录）。
  - 单测：http 放行/内网拒绝/伪造 DNS 桩、open_url 拒绝与放行、确定性拒绝 attempts==1、
    瞬时失败仍满退避、端到端 open_app 拒绝零 retry。
  - 实机验证：重放首动作即 `open_url("https://www.baidu.com")` → medium 审计 →
    1 轮打开（晚场同位置烧 5 轮）；全程零无谓 retry。

## T1（P0）修复 `mail_remote` 首跑校准的并发隐患

- **文件**：`mail_remote/__init__.py`
- **证据行号**（已复核）：
  - `start()` 启动后台 daemon 轮询线程 → `:154`
  - `first_run = self._store._validity != validity`（无锁读、跨对象摸私有属性）→ `:252`
  - `ensure_validity` → `:253`、`mark` → `:263`（与判定不在同一临界区；`_poll_once` 全程未持 `self._lock`）
- **问题**：`first_run` 的"判定 + 落 validity + 去重 mark"三件事分两处、无统一锁，后台线程与直接调用并发时，历史邮件可能被当作新邮件"执行"而非"校准"，破坏其要防的**旧邮件重放**安全场景。生产为单线程 60s 轮询，几乎不触发；主要暴露为测试偶发失败（本次复核 6 连跑未复现，报告实测复现 1 次——典型竞态特征）。
- **修改方案**：
  1. 在 `_SeenStore` 中新增原子方法：`observe(validity, uid) -> "calibrate" | "execute" | "seen"`，把判定/落值/去重 mark 包进同一把锁；
  2. `_poll_once` 调用 `observe()` 取得状态后再决定校准还是执行，删除 `:252` 的无锁私有属性读取；
  3. 测试侧：不再在 `start()` 后直接同步调 `_poll_once()`（或先 `stop()` 后台线程），消除竞态来源；保留该用例作为回归保护。
- **验收标准**：
  - 核心套件实跑 `243 passed, 7 xfailed`，连跑 10 次无抖动；
  - 原子方法单测覆盖三种返回态（`calibrate/execute/seen`）。
- **预估工时**：0.5h　**依赖**：无
- **实施记录（2026-10-01，客户机执行，已完成）**：
  - `_SeenStore` 新增 **`observe_batch(validity, uids) -> ["calibrate"|"execute"|"seen"]`**：
    首跑判定 + 落命名空间 + 去重登记在同一把锁内原子完成；`observe()` 为单信薄封装
    （覆盖验收要求的三返回态）。批量接口是必要的——逐信 `observe()` 会在同一批
    历史信里"第一封 calibrate、其余 execute"，破坏整批校准语义，故判定以批为单位。
  - `_poll_once` 重写：删去 `:252` 无锁私有属性读取与 `ensure_validity`/`already`/
    `mark` 三段式，改为"取信 → `observe_batch` → 按判定分发"。**顺带修复一个
    修复前就存在的次生隐患**：原实现 `ensure_validity` 先于 `fetch_new`，若校准后
    取信失败，下一轮 `first_run` 恒为 False，历史旧信会被当新信执行（正是本机制
    要防的重放场景）；现校准只在真正取到信时提交。`ensure_validity` 已无调用方，
    随之移除（职责并入 `observe_batch` 空批路径——首跑空收件箱仍会落命名空间）；
    `mark/already` 保留（测试与外部语义仍在用）。
  - 新增单测 ×2：`test_seen_store_observe_three_states`（三返回态 + 落盘重载 +
    换命名空间重新校准）、`test_observe_batch_concurrent_calibrates_once`
    （8 线程屏障并发同一新命名空间：恰好一个批次校准、execute 恒为 0）。
  - 验收实测（客户机 py 3.13.15 / pytest 9.1.1）：核心 8 文件 **245 passed,
    7 xfailed**（原竞态用例转为确定性通过）；裸跑全仓 **273 passed, 7 xfailed

    （N 个参数 → testpaths 被收 N 遍，见文末环境留痕），验收以裸跑口径为准；

## T11（P1·新）Chrome 上 UIA 控件操作单次可达 2 分钟，成为新的耗时大头

- **发现**：2026-10-01 重放实测（audit-20261001.jsonl）。
- **证据**：同一任务内 `click_ui_element` 执行 **121.0 秒**、`list_ui_elements` 执行
  121~127 秒/次；晚场任务反而没这问题（当时开浏览器就烧光了轮次，根本没走到 UIA）。
  T6/T7 修掉"轮次浪费"后，Chrome 的 UIA 枚举成了新的墙钟大头——重放两轮各 12/24 轮
  都因累计 UIA 耗时触发重放脚本 10 分钟看门狗，而非轮次或 LLM 耗尽。
- **根因**：`agent_vision.py` 的 `win.descendants(control_type=…)` 用 pywinauto UIA
  后端遍历 Chrome 整个无障碍树；Chrome 的文档树极大且惰性构建，逐控件取
  `element_info/window_text()` 每次 100+ 秒。这不是参数问题，无"一行改超时"的修法。
- **修改方向（需独立评估拍板）**：
  1. 启动 Chrome 时带 `--force-renderer-accessibility`（或检测到 UIA 操作前先发
     WM_GETOBJECT 激活），实测常能把枚举从分钟级降到秒级——先做小样验证；
  2. SYSTEM_PROMPT 工作流提示：浏览器窗口优先 `analyze_screen`+坐标点击，
     `list_ui_elements` 留给记事本/资源管理器等轻窗口；
  3. `descendants` 结果按窗口句柄+焦点做短 TTL 缓存，避免同屏反复全树枚举。
- **验收标准**：Chrome 前台下 `list_ui_elements` 稳定 ≤15 秒；重放任务 1 全程
  墙钟 ≤3 分钟。
- **预估工时**：0.5–1d　**依赖**：无（建议在 T4 之前，它直接决定实机可用性）

  archive/test_stability_e2e.py:251 [high] 路径穿越（report_file），

- **证据**：
  - `agent_loop.py:1506` (`save_config`): `config_path = script_dir / "agent_config.json"`

  - `archive/test_stability_e2e.py:251`: `report_file = f"t8_stability_report_{int(time.time())}.txt"`
    → `open(report_file, "w")` 使用相对路径，可逃逸到任意位置。
  - `archive/test_stability_e2e.py:104/105`: `random.randint(1, 100)` 使用系统随机，
    不具备可重复性，影响测试稳定性。
- **根因**：
  - Path 操作未调用 `resolve()`，相对路径在当前工作目录变化时可能指向错误位置。
  - 测试脚本使用时间戳生成文件名，但未指定绝对路径，依赖工作目录。
  - 测试脚本使用系统随机，缺乏可重复性。
- **修改方案**（已在本轮 T11 修复 agent_loop.py，test_stability_e2e.py 待排期）：
  1. **agent_loop.py**：
     - `screenshot` 工具：`Path("screenshots")` → `Path("screenshots").resolve()`
     - `verify_file_exists` 校验：`Path("screenshots")` → `Path("screenshots").resolve()`
     - `load_config`: `script_dir / "agent_config.json"` → `script_dir.resolve() / "agent_config.json"`
     - `save_config`: `script_dir / "agent_config.json"` → `script_dir.resolve() / "agent_config.json"`
  2. **test_stability_e2e.py**：
     - `report_file` 使用绝对路径：`Path(__file__).parent / f"t8_stability_report_{int(time.time())}.txt"`
     - 使用 `random.Random(seed)` 替代系统随机，确保测试可重复。
