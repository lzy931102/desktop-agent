## 2. P0 缺陷（不改就会让既定验收失败，或造成静默回归）

### P0-1　测试插桩点会断：§5 说"两个引用它的测试不用改"不成立

**证据**：`test_agent_loop_guard.py:70-71`

```python
monkeypatch.setattr(agent_loop, "TOOL_FUNCTIONS",
                    {"clipboard_write": stub, "press_key": stub})
```

它靠**替换模块级字典**来注入桩工具。§5 把执行路径改成 `self.tools.get(name)` 之后，
这个 monkeypatch 只改了模块属性，**改不到执行路径**（重导出的 `TOOL_FUNCTIONS` 从此变成只被测试读、运行时无人用的"假接口"）。

**逐用例后果**：

| 用例 | 断言 | 迁移后 |
|---|---|---|
| `test_medium_executes_with_audit_and_hint` | `len(stub.calls) == 1` | **FAIL**，且真的执行了 `clipboard_write` → **会写用户真实剪贴板** |
| `test_none_stays_silent` | `len(stub.calls) == 1` | **FAIL**，同上 |
| `test_high_goes_to_approval_and_denied` | `stub.calls == []` | **假绿**（拦截路径本来就不执行工具，断言恒真） |

`tests_smoke.py:122-123`（断言 `send_feishu_message` 在 schema 与 TOOL_FUNCTIONS 里）能靠重导出保住，**但这一条保不住**。

**修法**：`DesktopAgent` 必须留一个可替换的注入点。测试改为构造"只含桩插件的最小 PluginManager"传给 `DesktopAgent(plugins=...)`（或保留一层 `self._registry` 间接，测试 patch 它）。
**验收**：三条用例改完后仍能区分 high / medium / none（对照组语义不能丢）。

### P0-2　模块级 `_default_pm` 与"重启任务生效"自相矛盾，且违反工作准则

**证据**：`gui.py:248-255` —— 每个任务在工作线程里**新建** `DesktopAgent`；
而 §5 写 `_default_pm = build_default_plugin_manager()`（**import 时**构建一次）+ `self.tools = plugins or _default_pm`。

**后果**：GUI 是长驻进程，启动时 import 就固定了禁用集；用户改设置后**永远不生效**，
除非重启整个 GUI 进程。§6 步骤③的验收"禁用后 LLM schema 里看不到该工具"**必然失败**（这里"重启任务"≠"重启进程"）。

另外：`工作准则.md` 第三节第 1 条明确禁止"隐式全局状态"，模块级单例正是它。

**修法**：`DesktopAgent.__init__(self, ..., plugins=None, settings=None)`，未传时**在 `__init__` 内**按 settings 构建；
`_default_pm` 若仅为旧 import 兼容，应惰性求值（模块级 `__getattr__`）而非 import 时构建。
顺带修正措辞：`gui.py:254` 首版必须改一次（加 `settings=app.settings`），**"不改 gui.py"应表述为"日常增删工具不改 gui.py"**。

### P0-3　测试结果会随本机 settings.json 漂移

**证据**：`tests_smoke.py:122-123` 断言 `send_feishu_message` 在 `_al.TOOLS_SCHEMA` 与 `_al.TOOL_FUNCTIONS` 中；
而 §5 的这两个对象由 `_default_pm` 派生，`_default_pm` 读的是 `core.paths.data_dir()` 下的**真实** `settings.json`。

**后果**：用户一旦在插件面板关掉飞书插件，`tests_smoke` 就 FAIL，且与代码无关；
换台机器/换个人跑结果不一致（违反准则十.1 可复现性）。

**修法**：兼容重导出必须固定为**全量内置集**，不受用户禁用过滤；禁用只影响 `DesktopAgent` 运行时的 pm。
**验收**：`python tests_smoke.py` 在"全禁用"与"全启用"两种 settings 下结果一致。

### P0-4　`retryable: bool = True` 会让 3 个工具静默变成可重试

**证据**：`core/guard.py:73-79` `RETRYABLE_TOOLS` 实测 **18 项**；
21 个工具中**不在**其中的 3 个是：`analyze_screen`、`send_feishu_message`、`verify_message_sent`。
现行判定 `agent_loop.py:826`：`retryable = risk != "high" and guard.is_retryable(name)`。

**后果**（迁移即静默行为变更）：

- `analyze_screen`：`guard.py:72` 注释明确"不重试：单次调用可达 1-2 分钟，重试只会加倍等待"。
  改默认 True 后最坏变成 3 次重试（退避 1+2+4s + 最长 3×2 分钟）——**把已拍板的设计改掉了**。
- `send_feishu_message`：未配置 webhook 时返回 `"错误: 未配置…"`，会连重试 3 次。
- `verify_message_sent`：校验类工具，重试无意义。

**修法**：契约默认改 `retryable: bool | None = None`，`None` = "查 `guard.RETRYABLE_TOOLS`"（保持单一真相），
显式 True/False 才覆盖；迁移时加断言测试 `{插件 retryable} == guard.RETRYABLE_TOOLS`。
**待拍板项**：retryable 的真相该留在 guard 数据表还是搬到插件（见 §7-1）。

|---|---|---|---|

## 5. prompt 顺序：§7.1 与 §4 相互冲突（方案内部矛盾）

### 5.1 顺序不能统一按"文件声明顺序"

`_stat2.py` 实测（§1.3 已列）：

- schema 首 6：`click type_text press_key hotkey move_to scroll`（坐标类优先）
- prompt 首 6：`list_windows focus_window analyze_screen list_ui_elements click_ui_element open_app`（窗口优先）

若按 §4 的文件顺序输出（`mouse_keyboard.py` 排在第一位），**prompt 的第一条提示会变成 `click` / `type_text`**，
等于把"先看窗口、再点控件"的引导改成"先猜坐标点击"——这恰恰是本项目最核心的可靠性设计（对照 `SYSTEM_PROMPT` 工作流第 1、2、4 条）。

**修法**：schema 顺序与 prompt 顺序**分离**。schema 按域（保持现在的分组即可）；
prompt 顺序由显式优先级声明（如插件带 `prompt_rank: int`，或在 `base.py` 维护一张引导顺序常量表），并加"顺序快照测试"锁死。

### 5.2 "固定文案不含工具名"这个前提**不成立**

实测：`SYSTEM_PROMPT` 点名了 21 个工具中的 **19 个**（仅 `get_mouse_position`、`get_screen_size` 未被提及）。
工作流第 1~5 条与安全规则里大量点名，例如：

> "1. 了解环境：先 `list_windows` 看有哪些窗口……" / "3. ……「有哪些控件」用 `list_ui_elements`（点开菜单后可查菜单项）"
> "2. 应用响应慢时用 `wait` 等待" / "1. 发送消息后，必须调用 `verify_message_sent(你发送的原文)` 验证"

所以方案说"固定文案（工作流、安全规则、诚实汇报）留在 agent_loop.py"是有问题的：
**禁用某插件后，模型仍被 prompt 指示调用它**，§6 步骤③的验收目标直接被破坏。

**修法**：把"点名工具的工作流提示"也纳入插件（`workflow_hint`），或按启用集过滤渲染；固定文案只留不依赖具体工具的流程原则。

## 7. 待拍板（本报告不给结论，列选项与影响）

1. **retryable 的单一真相放哪**：guard 数据表（现状、零改动） vs 插件声明（内聚、但要防双轨）。
2. **risk 兜底语义**：第三方插件 `default_risk="medium"` 会让**每次调用都写一条 `medium_risk` 审计 + 界面提示行**（`agent_loop.py:989-994`）——审计噪音 vs 可追溯性，选哪个。
3. **是否保留 `TOOLS_SCHEMA`/`TOOL_FUNCTIONS` 重导出**：保留 = 兼容但双轨（且 P0-1 的"假接口"问题仍在）；删 = 干净但要改 `tests_smoke.py` 与 8 个脚本。建议保留一期、下期删（呼应方案 §7.5）。
4. **`agent_vision` 定位**：推荐本次明确"原地不动、插件薄封装"；若要真拆，需同时改 `core/verify.py:117` + `gui.py:19/1142` + spec，风险另计。
5. **插件粒度**：§2 说"一文件一插件"，§4 却是"一文件多工具"。建议明确为 **模块 = 域（文件）/ 实例 = 工具（ToolPlugin）**。
