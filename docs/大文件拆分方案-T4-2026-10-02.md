## 1. 拆分原则（两轮共用）

1. **纯搬运，零逻辑变更**：只移动代码 + 调整 import，不改函数体、不重命名、不"顺手优化"。执行中发现的新问题按工作准则"发现与修改分离"，记入清单另立项。
2. **门面兼容**：原文件保留为门面，显式列出再导出清单（**禁用 `import *`**——会丢下划线名，如测试依赖的 `_wait_tool/_open_app/_create_folder`）。
3. **每步一个提交**：单步 = 一次物理搬运 + 全量验证 + git 提交（工作准则§七）。出问题单步回退。
4. **叶子→根顺序**：常量/提示词等无依赖模块先走，杜绝循环依赖（依赖图见 §2.7 / §3.7）。
5. **单文件上限 ~700 行**：TOOLS_SCHEMA 这类纯静态数据允许独立成文件不计入复杂度。
6. **每步验证口径**：`pytest`（按 pytest.ini 只收集根目录，给全量 PASS 数对比基线）+ `python -c "import gui, agent_loop"` + GUI 冒烟（第二轮每步跑）。

## 2. 第一轮：拆 agent_loop.py（1600 行 → 门面 ~50 行 + 5 个顶层模块）

**顺序理由**：agent_loop 是 gui 的被依赖方（C1），先拆它并把门面立稳，第二轮 gui 的子模块照旧 `from agent_loop import …` 即可，两轮互不牵连。

新模块用**顶层平铺**（与 `agent_vision.py`、`mail_remote.py` 惯例一致），**不用子包**：这些模块全是网络/桌面操作出口，顶层 `*.py` 被策略扫描测试自动覆盖（C5），零测试改动。

## 3. 第二轮：拆 gui.py（3244 行 → 门面 ~80 行 + `ui/` 包）

**核心策略**：独立类直接搬走；2421 行的 AgentGUI 按**职责拆 Mixin**——方法原样搬进 Mixin 类，`AgentGUI(CoreMixin, EventsMixin, …)` 组合在门面里。选 Mixin 而非组合（controller 注入）的理由：所有方法仍以 `self` 访问共享状态与互相调用，**零行为变更、零 `self.` 改写**；C4b 的 `AgentGUI.__new__` + 未绑定方法调用经继承解析照常工作；可按方法组一个 Mixin 一个提交地渐进走。Mixin 之间无同名方法，MRO 无歧义。

新 UI 模块放 **`ui/` 包**（gui 子模块多，顶层已拥挤；有 `plugin_system/` 等包先例）。`ui/` 需加入策略扫描列表 `_POLICY_SCAN_SUBDIRS`（test_agent_loop_guard.py:354 加一项；UI 层无直接出网点，此改动是防御性的，防未来有人在 UI 层直连网络）。
