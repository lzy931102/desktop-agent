# verify_click 判定收紧设计（REL-P1-4）

> 任务 17 设计先行稿，2026-09-30。实现与本设计不一致处以代码注释为准并回写本文。

## 1. 背景与问题

`core/verify.py` 的 `verify_click` 是点击动作后唯一的校验手段：1.2 秒后全屏截图，
≥0.4% 像素变化即判"生效"。两种假象：

- **假通过**：计时器/动画界面自身就在变，点击落空也"通过"——校验给虚假安全感；
- **无分级**：像素证据是唯一证据，不区分"点在按钮上"和"点在空白处"。

后果：确认弹窗按钮点没点上模型不知道；静态界面的真落空会触发重试，而重试本身就是
连点风险来源——所以重试必须只在"确定什么都没发生"时才安全。

## 2. 范围

- 只收 `click(x, y)`（裸坐标点击）。`click_ui_element` 不在本次：它按名称经 UIA 点击，
  点击时本身有元素存在性断言，后置校验另行立项。
- 非关键点击维持现行为（像素对比），不加标注、不进重试环——控制改动面，也保住
  基线测试不倒退。

## 3. 关键点击定义（点击前，UIA ElementFromPoint）

点击执行前在同坐标做一次 `UIAElementInfo.from_point(x, y)`：

- `control_type ∈ {Button, MenuItem, CheckBox, RadioButton, Hyperlink, ListItem,
  TabItem, TreeItem, DataItem}` → **关键点击**，走强校验；
- 其它类型（Pane/Document/Text/空白/桌面根）→ 非关键，走现行为；
- UIA 不可用（pywinauto 缺失、COM 查询失败、提权窗口拒答）→ 回退现行为，
  结果标注"弱校验"。

刻意最小化 pywinauto API 面：只用 `ElementFromPoint` + `GetFocusedElement` +
`runtime_id`，不碰 Invoke/Toggle 等 pattern（CheckBox/Radio 的点击通常伴随焦点
迁移，焦点信号已覆盖；toggle 翻转断言列为将来扩展）。

## 4. 强校验信号（点击后同窗口 1.2s，任一成立 → 强通过）

1. **目标元素消失/被替换**：同点再查 `from_point`，`runtime_id` 与点击前不同
   （典型：确认弹窗关闭、菜单收起）；
2. **键盘焦点迁移到目标控件**：点击前焦点不在目标上，点击后 `GetFocusedElement`
   的 runtime_id == 目标 runtime_id（Windows 点击落地的惯常效果，**对动画免疫**；
   点击前焦点已在目标上时该信号不可用，不误判）。

runtime_id 的可用性依据：UIA runtime id 在元素存活期内稳定，同一可见元素重复
查询返回同值；对话框关闭后同点会命中下层不同元素。

## 5. 判定矩阵（关键点击）

| 强信号 | 像素变化 | 判定 | 后续 |
|---|---|---|---|
| 任一成立 | 不看 | **通过（强校验）** | 原样返回 |
| 均不成立 | 无 | **失败（确定落空）** | 进既定重试策略 |
| 均不成立 | 有 | **通过（弱校验，标注）** | 不自动重试，标注交回模型 |
| after 阶段 UIA 不可用 | 有/无 | 回退纯像素判定 | 结果标注"弱校验" |

设计要点：**自动重试只发生在"控件无变化且像素无变化"的确定落空场合**——此时
重试无双击/重复提交风险（第一次什么都没触发）；"元素没变但界面在变"（发送按钮
点了、消息出现，按钮还在）绝不自动重试——那是重复提交风险，标注"弱校验"把
判断交回模型。

## 6. 与重试层的衔接

强校验放进 `run_with_retry` 的执行函数内：物理点击 → 强校验，失败返回"错误: …"
即按既定退避（1s/2s/4s，最多 3 次重试）重跑点击+校验。click 本就在
`guard.RETRYABLE_TOOLS`。每次校验（含强弱档）发一条 `verify` 审计事件。
耗时预算：最坏 4 次尝试 ≈ 4×(点击+1.2s)+退避 7s ≈ 14s，仅发生在反复确定落空的
场合。

## 7. 残余风险（如实）

- 动画界面 + 目标控件无任何反应的点击 → 落在弱校验档，仍会通过，但带标注，
  不再是干净的"通过"；彻底消除需视觉确认（analyze_screen），成本另算；
- 点击前元素已移动/消失的竞态：after 同点查到别的元素 → 强信号误通过。窗口期
  毫秒级，远好于现状的全屏像素判据；
- 自绘 UI（游戏/部分 Electron）焦点信号缺失、UIA 树不可读 → 自然落到回退档；
- 提权窗口 UIPI 拒答 → 查询异常 → 回退档。

## 8. 测试计划

- `test_core_guard.py`：目标分类（Button→critical / Pane→plain / 异常→unavailable）、
  强校验判定矩阵（强两路、确定落空、弱两路、回退档）、像素比对函数本体
  （pyautogui.screenshot 打桩，不碰真实屏幕；time.sleep 打桩零等待）；
- `test_agent_loop_guard.py`：假 LLM 驱动 click——确定落空触发重试（attempt≥2、
  retry/verify 审计事件落链）、弱校验不重试且标注进结果、plain 点击走旧校验路径；
- 核心套件不倒退（基线 223 + 新增）。

## 9. 拍板记录

- 校验进重试环仅限关键点击；非关键维持"校验失败只标注不重试"的旧行为；
- 不纳入 toggle pattern 断言（API 面控制，焦点信号覆盖主要场景），记为将来扩展；
- 不给 click_ui_element 加后置校验（范围外，另行立项）。

## 10. 实机验证记录（2026-09-30）

- **抓到并修复一个真 bug**：`GetRuntimeId` 方法在原始 COM 元素上，UIAElementInfo
  包装对象没有——第一版 `_runtime_id` 对包装对象永远 AttributeError→None，critical
  分类整体失效（全部误判 plain）。单测全绿（桩对象自带 GetRuntimeId），实机冒烟
  才暴露。修复后 `_runtime_id` 兼容两种形态，COMError 哨兵 0 按无信号处理；回归
  测试 `test_runtime_id_handles_both_shapes` 锁死。
- **真实 Win32 对话框验证**：MessageBox 确定按钮 → critical 分类、rid 正常读取、
  强校验三路查询成功；未点击场景按矩阵正确落在弱校验档（像素有变化但控件无变化
  ——顺带实测确认了"环境像素变化确实不能当点击落地证据"）。
- **Win11 现代 UI（任务栏/WinUI）实测**：XAML 自绘控件的同点命中多为子层 Pane →
  分类保守回落 plain → 维持像素校验。安全方向（不会误判强失败），代价是这类界面
  暂时享受不到强校验；经典 Win32 对话框（确认弹窗等本任务的目标场景）不受影响。
