## 0. 总评

**这是一个"产品感觉好于工程纪律"的项目：代码内核和界面文案的水准明显高于同类个人项目，
但仓库管理层的欠账（.env 密钥入库、__init__.py 被忽略、大量改动不提交）已经从"隐患"
升级为"确定性事故"，其中一条会让任何人克隆仓库后程序直接起不来。**

一句话概括：会话内体验（对话流、反馈、文案、安全确认）接近成品软件水平；
系统级体验（首次启动、设置面板可达性、停止语义、错误文案准确性）还有硬伤；
工程卫生（提交纪律、.gitignore、文档同步）是当前最大的失分项。

## 1. P0（会造成确定性损害，必须立即处理）

### P0-1　真实 API Key 已提交进 git 仓库与历史（本次新发现，前三轮评审均未列出）

**证据**：

```
$ git ls-files | grep -i env
.env                                  ← 已被追踪

$ cat .env
BIGMODEL_API_KEY=ad7e...（真实密钥，本报告不重复全文）

$ git log --oneline --all -- .env
f39b40c chore: 添加 BigModel API Key 配置
```

`.gitignore` 第 3 行虽然写了 `.env`，但**对已追踪文件不生效**——密钥本体在提交
f39b40c 里，且已进入 git 历史。README 指向公开 GitHub 仓库
（github.com/lzy931102/desktop-agent），一旦推送过，密钥即视为泄漏。

**修法（顺序不能反）**：
1. 先到智谱控制台**作废并轮换这把 Key**（轮换是唯一可靠的补救）；
2. `git rm --cached .env` 并提交；
3. 若该仓库已推送远端，需用 `git filter-repo` 清历史或直接作废仓库重建。

### P0-2　`.gitignore` 仍在吃 `__init__.py`，且与一个新引入的自引用缺陷叠加后，
### 干净克隆下**整个程序无法启动**（严重度较前两轮评审升级）

**证据**：

```
$ git check-ignore -v core/__init__.py plugin_system/__init__.py skill_system/__init__.py phone_bridge/__init__.py
.gitignore:26:_*.py   ← 四个包全部命中（第三轮复核时是 2 个，现在波及 4 个）

$ git ls-files | grep __init__
（空）
```

`.gitignore` 第 26 行 `_*.py`（本意忽略临时脚本）匹配了所有 `__init__.py`。
这个问题在 09-26 评审列为 P0-1、09-28 复核仍 P0-1，至今未修，且波及面从 2 个包扩大到 4 个。

**为什么严重度升级了**：v2.0.14 在 `agent_loop.py:47-51` 的 skill_system 导入兜底分支里
写了一行自引用：

```python
try:
    from skill_system import SkillManager
except ImportError:
    SkillManager = None
    TOOLS_SCHEMA = TOOLS_SCHEMA  # 避免未定义引用   ← 这行恰好在导入期执行
```

`TOOLS_SCHEMA` 在第 447 行才定义，而 except 分支在导入期（第 51 行）就要执行它——
**这行"防御"本身必抛 `NameError`**。完整因果链：

干净克隆 → 各包缺 `__init__.py` → `from skill_system import SkillManager` ImportError
（`skill_system/__init__.py` 承担全部导出，没有它命名空间包里没有这个名字）
→ except 分支执行 `TOOLS_SCHEMA = TOOLS_SCHEMA` → NameError → agent_loop 导入失败
→ gui.py 第 22 行导入 agent_loop 失败 → **双击 exe 源码版直接起不来**。

本地全绿（文件都在磁盘上）、远端必坏，是三轮都漏过的同一类"本地照常、克隆即炸"问题。

**修法（一分钟）**：

```bash
# 1) .gitignore 第 26 行 _*.py 之后补一行（顺序不能反）
!**/__init__.py
# 2) 验证（应无输出）
git check-ignore -v core/__init__.py plugin_system/__init__.py skill_system/__init__.py
# 3) 补回四个包的入口文件并提交
git add core/__init__.py plugin_system/__init__.py skill_system/__init__.py phone_bridge/__init__.py
# 4) 同时删掉 agent_loop.py:51 那行自引用（它防的 bug 不存在，自身就是 bug）
```

### 2.2 问题清单（按用户受害场景排序）

#### UX-P1-1　设置面板固定 900px 高、不可滚动——在 1366×768 的笔记本上"保存"按钮够不着

**证据**：`gui.py:1895` `dlg.geometry("620x900")`；`:1898` body 是普通 CTkFrame，
**不是** CTkScrollableFrame，内容从上往下排到底（模型模式→并行数→本地→云端→看屏幕→
托盘→飞书→保存按钮，`save` 按钮在 `:2120`）。

**用户受害场景**：本项目目标用户画像明确包含中老年非技术用户（MUTED 配色注释为证），
这批人用 1366×768 老笔记本的比例很高。窗口高 900 > 屏幕高 768，系统会把窗口压到屏幕内，
**底部内容被裁掉且无法滚动**——用户改完 API Key 点不到"保存"，也不知道为什么保存不了。
这是"可操作"三个字上的硬伤。**修法**：body 换 `CTkScrollableFrame`，高度改
`min(900, 屏幕80%)`。

#### UX-P1-2　云端模式连不上时，错误文案说"连不上本地 Ollama"——用户被指向完全错误的方向

**证据**：`gui.py:941-947`：`if self.ollama_ok is False:` 后固定提示
"连不上本地 Ollama，请确认它已启动，我正在重新检测…"。而 `ollama_ok` 在云端/自动模式下
存的是云端连通状态（`:1333-1351`）。顶栏徽章 v2.0.14 刚刚专门改对了（"云端已连接/未连接"），
开始任务的错误提示却没跟着改。

**用户受害场景**：用户选了"只用云端"、填好 Key，点开始，提示让他"确认 Ollama 已启动"
——可他根本没装 Ollama，也永远装不上（或不想装）。这直接违反工作准则四.1
"错误提示要告诉用户发生了什么 + 能做什么"。**修法**：按 `settings.model_mode` 分支文案。

#### UX-P1-3　"选「否」可以最小化到托盘让任务继续跑"——在无托盘/关闭托盘开关时，选「否」直接退出、任务全被杀（第三轮点名，未修）

**证据**：`gui.py:1432-1443`：弹窗文案承诺"选否继续跑"；但 `:1438-1443` 在
`self.tray` 为空或 `minimize_to_tray=False` 时，选"否"走 `self._real_exit()`。

**用户受害场景**：用户特意选"否"想让它继续跑，结果进程退出、定时任务和正在执行的任务
全部中断。文案承诺与行为相反，是信任层面的伤害。requirements.txt 又恰好不含 pystray
（见 P2-5），pip 装依赖跑源码的用户大概率落到这个分支。

#### UX-P1-4　"停止"永远可能停不下来：wait 工具无上限 + 工具执行中不可中断

**证据**：`agent_loop.py:795` `wait: lambda args: (time.sleep(args.get("seconds", 1)) …)`——
模型传 `seconds=100000` 就睡 27 小时；停止标志只在每个 tool_call 之间检查
（`agent_loop.py:1072/1119`），工具执行中无超时、无中断。界面按钮停在"正在停止…"
（`gui.py:920`）没有超时兜底。

**用户受害场景**：模型一次幻觉输出超长 wait，用户点停止后按钮永远显示"正在停止…"，
鼠标还可能停在半路。**修法**：`wait` 上限钳到 60 秒；`_execute_tool` 增加超时包裹或
在工具内分段检查停止标志；"正在停止…" 超过 30 秒提示"当前步骤跑完就停，请稍候"。

#### UX-P1-5　设置面板两处线程问题（第二轮点名，未修）——违反项目自己的踩坑铁律

**证据**：
- `gui.py:2048-2059`：`run_test` 的 `work()` 在后台线程里直接 `test_result.configure(...)`
  ——`docs/踩坑.md` 条目 4 明令"所有 GUI 操作统一用 root.after"，主界面 ui_queue 改造
  （v2.0.12）修得很彻底，唯独设置面板这处漏网，偶发卡死风险仍在；
- `gui.py:2124`：`body.after(200, refresh_models)` → `list_models()` →
  `requests.get(timeout=5)` 在**主线程**发网络请求——Ollama 没启动时，打开设置面板
  界面冻结最长 5 秒。

#### UX-P1-6　首次启动的"最后一公里"没有在产品内完成

**证据**：默认 `model_mode="local"`（`core/settings.py:17`），本机模式必须先装 Ollama
（500MB+）并拉取 7B 模型（约 4.7GB）。应用内的引导只有：顶栏"○ Ollama 未连接"徽章 +
点开始时一句"连不上本地 Ollama，请确认它已启动"（`gui.py:943`）。没有下载链接、
没有"打开设置"按钮、没有云端替代路径的指引；README/DOWNLOAD.md 承担了本应由产品
承担的引导职责，但看 README 的用户和装 exe 的用户往往不是同一批。

**对比**：视觉部分 v2.0.14 已默认走云端（配置了 Key 就秒用），对话模型却仍是
"先装 Ollama"路线。对一个明确面向非技术用户的产品，首启体验应是云端优先：
**建议**首次检测不到 Ollama 时，弹一次可操作的引导卡（三选一：我看不懂→用云端（附
教程链接）/ 我要用本地（附 Ollama 下载直链）/ 稍后再说），并记住选择。

#### UX-P1-7　关闭"正在跑"的任务：文案说"停止并关闭"，实际鼠标可能还在动

**证据**：`gui.py:877-883`：`close_session` 在 running 状态下 `s.stop()` 后**立即**
`self.sessions.pop(s.id)`；工作线程还在跑（`TaskSession._run` 持有 agent 引用继续执行），
停止只在本轮 tool_call 边界生效。弹窗（`:879-881`）没说明"本轮跑完才真停"。

**用户受害场景**：用户确认"停止并关闭"后起身离开，以为没事了，鼠标仍在被操控。
**修法**：文案补"已发出停止请求，当前这步执行完就停"；关闭时给会话挂 finished 回调，
真正停稳后再从 UI 摘除（或至少在任务表里保留"正在停止"状态直到线程退出）。

#### UX-P1-8　错误文案的"最后一步指引"普遍缺失（对照工作准则四.1 抽查）

| 位置 | 现文案 | 缺了什么 |
|---|---|---|
| `gui.py:943` | "请确认它已启动" | 没说去哪下载/怎么算"已启动"（羊驼图标），没给"打开设置改用云端"出口 |
| `agent_loop.py:779` | "仅支持打开以下应用…" | 列了清单，好；但没告诉用户"别的应用可以让我从开始菜单找"，能力边界外没有出路 |
| `agent_vision.py:186` | "未配置云端 API Key（在「设置 → 云端模型」里填…）" | 这条是**好例子**，有位置有动作，值得作为全项目错误文案的模板 |
| `gui.py:1150` 读不到模型列表 | "请确认 Ollama 正在运行" | 同 943 |

结论：项目里已有正确范例（视觉那条），缺的是把"位置+动作"模板推广到全部错误出口。
