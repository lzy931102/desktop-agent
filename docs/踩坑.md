## 1. Tk `grab_set()` 在 Windows 上吞掉标题栏最小化消息

**现象**
对话框（CTkToplevel）调用 `grab_set()` 后，点标题栏「—」无任何反应；但「□」最大化和「×」关闭正常。主窗口（无 grab）最小化正常。

**根因**
Tk 在 Windows 上，grab 激活期间窗口收到标题栏 `WM_SYSCOMMAND / SC_MINIMIZE` 消息会被吞掉。最大化/关闭走不同消息路径，不受影响。

**规避/修复**
不要简单删 `grab_set()`（会丢模态语义）。改用 Windows 原生模态：`EnableWindow(parent_hwnd, False)` 禁用父窗口，对话框关闭时恢复。封装为 `attach_modal_dialog(dlg, root)`。

**验证**
- 红：修复前点「—」`showCmd` 恒为 1（normal），rect 不变
- 绿：修复后 `showCmd=2`（minimized），`SW_RESTORE` 可恢复
- `□`/`×`/主窗口「—」回归正常

**涉及文件**：`gui.py`（4 处对话框：任务表 / 历史 / 设置 / 定时）

## 2. `<Destroy>` 事件里 `event.widget` 不能用 `is` 身份比较

**现象**
对话框销毁时，靠 `<Destroy>` 事件解除父窗口禁用，但解除逻辑不生效，父窗口永久禁用（点不动）。

**根因**
对话框销毁时，事件里的 `event.widget` 是 Tk 新建的包装对象，与原来的 widget 对象不是同一个 Python 对象。`event.widget is dlg` 永远为 False。

**规避/修复**
改用**路径字符串比较**：`str(event.widget) == str(dlg)`。路径在销毁后仍稳定，身份比较不可靠。

**验证**
隔离实验：disable → destroy → 路径匹配 → RESTORED。真实应用：`F0` 探针确认主窗口 `IsWindowEnabled=1`。

## 3. 测试前必须清理环境，否则实验被污染

**现象**
最小复现实验反复失败，点击落空或窗口状态诡异。多次排查后发现是环境干扰。

**根因**
- 用户自己运行的 `DesktopAgent.exe` 实例（一个托盘隐藏、一个可见）与本项目无关，但窗口同名
- Windows 系统设置窗口标题也是「设置」，被误当成目标窗口
- 最大化对话框盖在最上层，实验点击全落在它身上
- pywinauto 枚举全桌面窗口不稳定，触发过 MemoryError

**规避/修复**
测试前按 PID + exe 路径过滤，确认目标窗口归属自己的进程；避免与用户运行的实例混淆。必要时把测试窗口放在屏幕空白区（x>1400），一次只测一个窗口。枚举窗口优先用纯 `ctypes`（`EnumWindows`），不用 pywinauto 全桌面枚举。

**验证**
按 PID 过滤后，窗口标题/位置/进程路径对应关系清晰，实验可复现。

## 4. 后台线程调 tkinter 会死锁

**现象**
探测脚本用后台线程调 tkinter API，偶发卡死（进程不退出、无输出）。

**根因**
tkinter 不是线程安全的，非主线程调用 GUI API 可能死锁。

**规避/修复**
所有 GUI 操作统一用 `root.after(ms, callback)` 调度到主线程执行，不在后台线程直接调 tkinter。

**验证**
改为无线程版本后，脚本干净跑完，无卡死。

## 5. 验收脚本点击被重叠窗口截走（z-order 假失败）

**现象**
验收脚本 F1（主窗口「—」）失败，怀疑是应用回归，实际是点击落在别的窗口上。

**根因**
窗口 z-order 不确定，`pyautogui.click(x, y)` 按屏幕坐标点击，若目标窗口被上层窗口遮挡，点击被截走。

**规避/修复**
点击前先把目标窗口前置并可选轻微移位：
- `SetWindowPos(hwnd, HWND_TOP, ...)` + `SetForegroundWindow(hwnd)`
- 若前台锁拒绝，临时 `HWND_TOPMOST`，点完取消
- 挪位后**必须重读 rect 再算坐标**
- 加 `time.sleep(0.4)` 等 z-order 稳定

**验证**
置顶后手工复测主窗口「—」→ `showCmd=2`，PASS。

## 6. Python 3.14 的 `ctypes.wintypes` 没有 `WINDOWPLACEMENT`

**现象**
验收脚本用 `ctypes.wintypes.WINDOWPLACEMENT` 报 AttributeError。

**根因**
Python 3.14 的 `wintypes` 未提供 `WINDOWPLACEMENT` 结构体。

**规避/修复**
手动定义结构体：

```python
class WINDOWPLACEMENT(ctypes.Structure):
    _fields_ = [
        ("length", wt.UINT),
        ("flags", wt.UINT),
        ("showCmd", wt.UINT),
        ("ptMinPosition", wt.POINT),
        ("ptMaxPosition", wt.POINT),
        ("rcNormalPosition", wt.RECT),
    ]
```

## 7. 安全钩子误报"路径穿越"：可变路径文件操作被拦（来源：任务 16 fetcher.py）

**现象**
Edit 重写 `phone_bridge/fetcher.py` 的 `download_cloudflared` 两次被 Mimosa 钩子拦为「高危·路径穿越」。文件里没有任何 `../`；两次报的行号（93、21）分别落在 `while True:` 和 `import ssl` 这类无关语句上——报点漂移，定位不可信。同文件旧写法（`open(tmp, "wb")` + `shutil.move(str(tmp), str(dest))`）此前已在库里，说明是"重写触发写时扫描"才被拦。任务 12 有同类先例（`open(变量)` 被标记，判定误报）。

**根因**
钩子对"内建/工具函数 + 可变路径参数"的形态敏感（`open(变量)`、`shutil.move(变量, 变量)`），建议文案固定为「规范化并校验路径」，与具体代码内容关系不大。模式匹配必有误报率，且报点不可信——**别按它报的行号去查**。

**规避/修复**
按钩子建议做了**真实加固**（不是绕过），同时换成合规写法（Read + Write 路径）：
- `tools_dir()` 返回 `resolve()` 后的绝对路径；
- 临时文件与目标文件做**同目录包含校验**：`tmp.parent != dest.parent` 即拒绝——防穿越的本质是规范化后校验目标在允许目录内，不是看字面有没有 `../`；
- `shutil.move` 改 `tmp.replace(dest)`（os.replace 语义，同卷原子替换）——顺带消除旧写法 `dest.unlink()` → `move(...)` 之间目标文件短暂缺失的窗口；
- 内建 `open(tmp, "wb")` 改 `tmp.open("wb")`。

归因备注（如实）：最终放行时同时变了两个变量——①上述等价改写 + 加固，②Edit 换 Write 工具——**无法单独归因**，复盘按"组合拳"记录。

**验证**
放行后 py_compile 通过、全套测试通过；`test_phone_bridge.py` 的下载用例覆盖 resolve/同目录校验路径，行为与改写前等价。

## 8. 验收脚本的同步打桩会把多批次状态压进单个事件批（来源：任务 16 实机脚本）

**现象**
实机验收脚本报「手机任务没落成 TaskSession」（FAIL 11/19a），但诊断 dump 显示会话其实已存在且已 done——轮询断言结果与系统真实状态矛盾；总检查数比预期少 2，实为 `if s:` 守卫把两条断言静默跳过。

**根因**
`TaskSession.launch` 的生产契约是"起线程、立即返回"。首轮打桩把假体写成**同步函数**且体内 `time.sleep(3)`——它在 `root.update()` → `_create_session` → `s.launch()` 路径上**原地睡在主线程**；醒来后把 done 塞进 ui_queue，同一个 `update()` 批次里 `_pump` 随即消费、`_phone_forward` 弹掉对照表条目。创建与完成被**合并进同一个事件批**，轮询条件（在两次 update 之间检查映射表）永远看不到本应存在约 3 秒的中间状态窗口。关键认知：**即使假体瞬时返回不睡，done 的消费仍发生在同一批次里，照样失真**——问题不在"卡住"，在"并发形态被压扁"。

**规避/修复**
给异步函数打桩，桩必须复刻线程边界：`fake_launch` 里 `threading.Thread(target=self._fake_run, daemon=True).start()`，假体函数体跑在后台线程。事件经真实的跨线程交接（ui_queue + 120ms `_pump`）落进不同批次，中间状态窗口可见。一句话：**打桩保真的是并发契约，不只是行为与返回值**。

**验证**
线程化打桩后实机脚本 22 项全 PASS，此前"矛盾"的失败全部转绿。

**附加教训**
- 轮询断言失败时症状会撒谎（FAIL 的是 11/19a，根因在打桩层）：先 dump 全量状态（会话表/映射表/hub 状态）再猜；
- 检查总数变少 = 有断言被守卫跳过，本身就是重要信号，别只看 PASS/FAIL 行。

## 9. type_text 盲粘进用户自己的文档（来源：T30，2026-10-05 事故实录）

**现象**
用户开着记事本（3 个标签、含未保存的自己的文件），Agent 跑"打开记事本，输入 你好"——`Ctrl+V` 把"你好"粘进了**用户自己的文件**，任务还报"任务完成"。audit 哈希链显示全程只有一次 `type_text` 调用，排除模型连点；无标题记事本里累积出 5 份"你好"是同一机制（多次任务的盲粘全落进当时前台的那个残留窗口）。

**根因**
两层叠加：
- `type_text` 是 `pyperclip.copy + Ctrl+V`，粘给**当时前台窗口**，而项目 2026-10-03 已实测"后台进程 startfile 拉起的应用不抢前台"（agent_loop `_capture_app_window` 注释）——新记事本没到前台，粘贴就进了用户的前台窗口；
- `verify_open_app` 只查"屏幕上有没有标题含'记事本'的窗口"，用户已开的窗口直接让它假阳性通过，新窗口根本没出现也报"窗口已出现"。

**规避/修复**
- `type_text` 粘贴前焦点校验（T30）：dispatch 把 T22 开窗记录搭载给工具（`args["_agent_opened"]`），取最近一个成功抓到的 app hwnd 作锚定；`_ensure_foreground(hwnd)` 用 `SetForegroundWindow` + 轮询 `GetForegroundWindow` 比对（被前台锁拒绝时 `AttachThreadInput` 附加前台线程重试，同本文件 #5 的 TOPMOST 先例）；前台不是目标 → 返回"错误: 前台是「X」，不是目标「Y」，已拒绝输入（不盲粘）"，剪贴板键盘一次都不碰。成功回显补"→ 已输入到「窗口标题」"，模型粘错目标能当场发现。无锚定（本任务没成功 open_app 过，如开始菜单敲字流程）保持原行为可输入，回显同样报接收窗口。
- `verify_open_app` 改差集：dispatch 在 `open_app` 动作前 `snapshot_windows()` 取 (hwnd, 标题) 快照，校验只认"快照之外新出现的 hwnd 且标题命中"。**差集必须按 hwnd 不按标题**：记事本的 `*` 未保存标记异步刷新，标题差集会把已有窗口的标题变化误判成新窗口（手动验证实测踩中后返工）。
- System Prompt 与工具描述加规则："输入文字前确认前台窗口是目标窗口，不匹配就报错拒粘，禁止盲粘；报错时先 list_windows 弄清状态，不要原样重试"。

**验证**
- 红灯：新测试在未修代码上 `TypeError: _type_text_with_space() got an unexpected keyword argument 'target_hwnd'`，复现"无锚定校验"缺口
- 单元 15 条全绿（拒粘不碰剪贴板/键盘、拒粘不得再拼"已完整输入"回显、同名标题新 hwnd 认得出、旧窗口标题变化不误判、无快照保持旧行为）
- 手动（`e2e/test_t30_focus_manual.py`，10/10）：先开记事本 A 模拟用户窗口，Agent 流程开 B，`type_text` 锚定 B → 前台切到 B、B 标题出现 `*` 且把粘贴首行当文档名、A 标题不变；锚定已关闭 hwnd → 拒粘两窗口标题都不变；verify 差集双向正确
- 全量门禁 401 passed / 0 failed / 7 xfailed（基线 386P + 新增 15P）
